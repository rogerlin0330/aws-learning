# ECS – Concepts & Cluster Modes

## What ECS Is

The **Elastic Container Service (ECS)** is a managed, container-based compute service. You can always run containers yourself by installing the Docker engine on a raw EC2 instance — but ECS takes away most of the admin overhead of self-managing your container hosts.

> **Mental model:** ECS is to containers what EC2 is to virtual machines.

You hand ECS your container images plus some instructions, and ECS orchestrates **where** and **how** to run them. It runs in one of **two cluster modes**, which radically change how things work under the surface:

|Mode|Container hosts|Who manages the hosts|
|---|---|---|
|**EC2 mode**|Normal EC2 instances running the ECS software (visible in your account)|**You** (with ECS tooling)|
|**Fargate mode**|Serverless — AWS-managed shared infrastructure|**AWS**|

The high-level building blocks below apply to **both** modes.

---

## The Core Hierarchy

A consistent way to think about the ECS building blocks:

> **Service** = a _distributed_ thing — runs and manages many copies of an application. **Application** = a **task** — the application as a whole; contains one or more modules. **Module** = a **container** — a single component, defined by a container definition.

So the nesting is: **Service → (many) Tasks → (one or more) Containers**.

Building these up from the bottom:

### 1. Container Definition (the _module_ pointer)

A **container definition** describes a single **module (container)**. At the associate level, remember it as essentially a **pointer**:

- **Which image** to use (and **where** it lives — i.e. its container registry).
- **Which port(s)** are exposed (e.g. port 80 / HTTP).

It does a few other things too, but image + ports is the exam-level summary. Everything else lives in the task definition.

### 2. Task Definition (the _application_)

A **task** represents a **self-contained application as a whole**. A task can bundle:

- **one module (container)** — e.g. a simple web app, _or_
- **many modules (containers)** — e.g. a web-app container **plus** a database container.

The task definition stores the container definition(s) that make up that one application, **plus** application-wide settings:

- **Resources** — CPU and memory.
- **Networking mode**.
- **Compatibility** — whether the task runs on EC2 mode, Fargate, or both.
- **Task role** ⭐ — see below.

> ⚠️ **Trap / confusion point:** When you create a task definition in the ECS UI, it creates a container definition _along with it_, and many tasks contain only **one** container. Architecturally they are still **separate things** — a task can include **one or more** containers.

#### Task Role ⭐ (high-probability exam point)

A **task role** is an **IAM role that a task can assume**. On assuming it, the task gets **temporary credentials** that any module (container) inside that task can use to access AWS products and services.

> **Best practice:** The task role is _the_ recommended way to give containers in ECS permissions to access AWS services. **Expect at least one exam question on this.**

### 3. Service Definition → Service (the _distributed_ layer)

A bare task **does not scale on its own** and is **not highly available** by itself. You _can_ run a single standalone copy of a task, but to get scaling and resilience you wrap it in a **service**, configured via a **service definition**.

A **service** is the _distributed_ layer that manages **many copies of the same application (task)**. It provides:

- **Scaling** — define how many copies of the task to run (e.g. "run 5 copies").
- **High availability / resilience** — multiple independent copies; **replaces failed tasks**.
- **Load distribution** — put a **load balancer** in front so incoming load is spread across all tasks.
- Other controls — restarts, certain monitoring features.

> **When to use a service:** long-running, **business-critical / production** applications that must handle substantial incoming load. For a quick single-copy run (like a simple demo), you can deploy a lone task with no service wrapper.

**What you deploy into a cluster:** tasks **or** services — and this is identical for EC2-based and Fargate-based clusters. You create a **cluster**, then deploy tasks or services into it.

## Container Registry & ECR

Container definitions point at images stored on a **container registry**:

- **Docker Hub** — public registry example.
- **ECR (Elastic Container Registry)** — AWS's own registry. Benefit: integrated with AWS, so the usual **permissions and scalability** benefits apply. At its heart it's just a container registry — use it or something else.

# Cluster Modes in Detail

Both modes share the same high-level **ECS management components**: **Scheduling & Orchestration**, **Cluster Manager**, and the **Placement Engine** (decides _which_ host runs each container). Both also use **registries** and the same **task / service definitions**. What differs is **how containers are actually hosted** — and therefore **what you manage** and **how you pay**.

## EC2 Mode

![[ecs-cluster-mode-ec2.png]]

### Diagram walkthrough

- **Top-left — ECS management components (dotted box):** The ECS logo sits beside the three shared control-plane functions: **Scheduling and Orchestration** (blue bar), and below it **Cluster Manager** and **Placement Engine** (green bars). These high-level components exist in **both** modes.
- **Top-right — definitions and Registry:** The two stacked list-style icons represent your **task / service definitions**. The purple arrow from **Registry** (the grid icon, far right) into the definitions shows that definitions reference **container images** pulled from a registry (ECR or Docker Hub).
- **Middle — ECS Cluster (orange dotted box):** The cluster is created **inside a VPC in your account**, so it spans the VPC's **multiple Availability Zones** — here **AZA** and **AZB**.
- **ASG marker (the orange 4-arrow icon):** The cluster's EC2 container instances are managed by an **Auto Scaling Group**, which handles **horizontal scaling** (add instances when needed, remove when not). The dotted line spanning the AZs indicates the ASG boundary across both zones.
- **Bottom — container-host icons:** The four box-with-chip icons are **EC2 instances acting as container hosts** (two in AZA, two in AZB — the example's "four container instances").
- **Purple arrows from definitions down into the hosts:** Via the **task / service definitions**, container **images are deployed onto the container hosts in the form of containers (modules)**. The arrows landing on instances in both AZs show ECS's placement engine distributing containers across hosts and AZs.

### Key facts — EC2 mode

- An ECS **cluster runs in your VPC** and benefits from **multiple AZs**.
- **EC2 instances are the container hosts.** You set an **initial size** (number of container instances) at cluster creation; an **Auto Scaling Group** handles horizontal scaling.
- These are **real EC2 instances** — you can **see them**, **connect to them**, and you **pay for them**.
- 💰 **Billing trap:** You pay for the EC2 container hosts **whenever they're in a running state — even if zero tasks/services are running on them.**
- **Not serverless.** You are responsible for the container hosts: **capacity, availability, scaling, sizing, and fault correction** (ECS provisions them, but expects you to manage them via ECS tooling).
- ECS _does_ manage some elements — e.g. the **number of tasks** if you use services/service definitions — but **cluster capacity** is on you.
- **Pricing flexibility:** Because they're EC2 instances, you can use **Reserved Instances** and **Spot pricing** — but you manage all of it yourself.
- **Positioning:** A **middle ground** — ECS removes a lot of container overhead, but you **keep** host-level control and flexibility.

## Fargate Mode

![[ecs-cluster-mode-fargate.png]]

### Diagram walkthrough

- **Top-left — ECS management components (dotted box):** Identical shared control plane as EC2 mode — **Scheduling and Orchestration**, **Cluster Manager**, **Placement Engine**. (In Fargate this is the **Fargate service** handling these.)
- **Top-right — definitions and Registry:** Same as before — your **task / service definitions** reference **container images** from the **Registry** (purple arrow). Definitions still define the **image, ports, and resource requirements**.
- **Bottom-left — Fargate Shared Infrastructure (orange box):** The Fargate cube logo plus the **six container-host icons** represent the **shared Fargate infrastructure platform** that AWS maintains for all Fargate users. Like EC2, **customers are isolated** — you draw from a **shared pool** but have **no visibility** of other customers.
- **Red dotted "Allocated Resources" arrow (definitions → shared infrastructure):** Your definitions are **allocated onto the shared Fargate platform**; this is where the containers (modules) physically run.
- **Right — VPC box (AZA / AZB) with the ENI / network-card icon:** Although tasks run on shared infrastructure, **from a networking perspective each task is injected into _your_ VPC**.
- **Purple arrow (shared infrastructure → VPC ENI):** Each task is **given an Elastic Network Interface (ENI)** with an **IP address inside your VPC**. From then on the task behaves like any other VPC resource — reachable from within the VPC, and from the **public internet** if the VPC is configured that way (e.g. **public subnets that auto-assign a public IPv4 address**).

### Key facts — Fargate mode

- **Serverless — no EC2 instances to manage.** No provisioning, no capacity planning, no host availability worries.
- 💰 **Billing model:** Because there are no hosts of yours, you are **not** paying for EC2 instances whether used or not — you **pay only for the container resources you consume** (based on what the containers use). **No visibility of host costs.**
- Uses the **same surrounding tech**: same control plane, same registries, same task/service definitions (defining image, ports, resources).
- **Shared infrastructure platform:** AWS-maintained, offered to all Fargate users, with **strong customer isolation** (analogous to running EC2 on shared hardware).
- **Networking:** Tasks run on shared infrastructure but are **injected into your VPC** via an **ENI** with a VPC IP; can get **public IPv4** if deployed into auto-assigning public subnets.
- **Customizable:** Deploy into a **new VPC** or your own **custom-designed VPC**; still uses a cluster spanning AZs.

# Choosing the Right Option

As a solutions architect (and for the exam), you should be able to advise between **three** options:

1. **EC2 natively** — deploy the application straight into an OS on an EC2 instance (no containers).
2. **ECS in EC2 mode** — containerized app on an EC2-based cluster.
3. **ECS in Fargate mode** — containerized app on Fargate.

### EC2 vs ECS

- **If you use containers → pick ECS.** If your business already uses containers for anything, ECS makes sense.
- Using a **raw EC2 + Docker** host is an **edge case** — fine for quickly _testing_ containers, but **almost never** a good idea for production.
- **Containers in general** make sense when you want to **isolate applications**, for **low-usage** apps, apps that **share the same OS**, or where you **don't need the overhead of full virtualization**.

### EC2 mode vs Fargate mode

|Scenario|Pick|
|---|---|
|**Large, consistent workload** + **price-conscious** (want Spot / Reserved / existing reservations)|**EC2 mode** — likely cheaper, _but only if_ you minimize the admin overhead (scaling, sizing, fixing faults)|
|**Large workloads** but **overhead-conscious** (care about minimizing management)|**Fargate** — no host exposure or management|
|**Small or burst-style** workloads|**Fargate** — pay only for capacity used; a constantly-running EC2 fleet wastes capacity for spiky load|
|**Batch / periodic** workloads|**Fargate** — pay per consumption; EC2 mode means paying for instances even when idle|

> **One-liner heuristics:**
> 
> - **Price** over effort, large/consistent load → **EC2 mode** (Spot/Reserved).
> - **Minimize management overhead** (any size), or **bursty / batch / periodic** load → **Fargate**.

# Exam Quick-Reference / Mnemonics

- **Hierarchy:** **Service** (distributed, many copies) → **Task = application** (one or more modules) → **Container = module** (defined by a container definition).
- **Container definition** = _pointer_ → **image + ports**.
- **Task definition** = the **application**: container definition(s) + **CPU/memory**, **networking mode**, **compatibility**, and the **task role**.
- **Task role** ⭐ = IAM role the task assumes → temporary creds → **best-practice** way for containers to access AWS services. _(Expect a question.)_
- **Service / service definition** = scaling + HA + load balancing across many task copies; used for **production / business-critical** workloads.
- **EC2 mode** = your EC2 hosts → you **pay even when idle**, you **manage capacity**, you get **Spot/Reserved** flexibility → _not_ serverless.
- **Fargate mode** = serverless shared platform → **pay only for consumed container resources**, **no host management**; tasks **injected into your VPC via an ENI**.
- **EC2 mode = price-conscious + large/consistent load; Fargate = overhead-conscious + small/bursty/batch.**
