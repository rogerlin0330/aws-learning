# Elastic Kubernetes Service (EKS) 101

> **Prerequisite:** This note assumes Kubernetes 101 knowledge (control plane, nodes, pods, kubelet, etcd, ephemeral storage). EKS-specific behaviour is the focus here.

---

## What EKS Is

EKS is **AWS's managed implementation of Kubernetes** — AWS takes the standard Kubernetes system and runs it as a managed service. The critical point: it's the **same Kubernetes you'd find anywhere else**, just extended to integrate well with AWS.

**Why this matters (exam angle):** Kubernetes is **cloud-agnostic**. The two main reasons to pick EKS are:

- You need containers but **don't want vendor lock-in**.
- You **already run containers on Kubernetes** (on-prem or another cloud) and want a managed AWS equivalent.

> 🎯 **Keyword trigger:** "cloud agnostic" / "avoid lock-in" / "existing Kubernetes" → **EKS**, not ECS.

---

## Where EKS Can Run

EKS isn't only an in-AWS product. The deployment modes are:

|Mode|What it means|
|---|---|
|**AWS**|Normal mode — EKS runs as a managed product inside AWS. _(Assume this unless told otherwise.)_|
|**AWS Outposts**|Conceptually a tiny version of AWS running on-premises.|
|**EKS Anywhere**|Create EKS clusters on-premises or anywhere else.|
|**EKS Distro**|The EKS product released as **open source**.|

> For exam purposes and this note, "EKS" means the **normal in-AWS deployment** unless a question specifies otherwise.

---

## The Control Plane

- **Managed by AWS** — you don't operate it.
- **Scales based on load**.
- Runs **across multiple Availability Zones** (resilient by design).
- **etcd** (Kubernetes' key/value store) is **also managed by AWS** and **distributed across multiple AZs**.

> 🎯 **Trap:** Both the control plane _and_ etcd are AWS-managed and multi-AZ. Don't attribute multi-AZ resilience only to the control plane.

---

## AWS Service Integrations

EKS integrates with AWS the way you'd expect a native product to:

|Need|AWS service used|
|---|---|
|Container images|**ECR** (Elastic Container Registry)|
|Load balancing (wherever K8s needs it)|**Elastic Load Balancers**|
|Security|**IAM**|
|Networking|**VPC**|

## EKS Cluster = Control Plane + Nodes

An **EKS cluster** means **the EKS control plane (AWS-managed)** **plus** the **EKS nodes**.

### Node Options

|Node type|Compute|Who manages provisioning / lifecycle|
|---|---|---|
|**Self-managed nodes**|EC2 (in a group)|**You** — billed at normal EC2 pricing|
|**Managed node groups**|EC2|**The product** handles provisioning & lifecycle|
|**Fargate**|Serverless|AWS — no instance provisioning, configuration, type selection, scaling decisions, or cluster packing optimisation|

**Fargate specifics:** You define **Fargate profiles**, which let pods start on Fargate. Conceptually similar to **ECS Fargate**. No need to choose instance type or worry about when to scale.

> 🎯 **Decision driver — choose node type based on requirements.** If you need any of the following, **verify the node type supports it before committing**: **Windows pods · GPU · Inferentia · Bottlerocket · Outposts · Local Zones**
> 
> ⚠️ Capability support varies by node type and **has negatively impacted real projects**. Always check the current AWS capability list rather than assuming.

## Persistent Storage

Recall from Kubernetes 101: **storage is ephemeral by default**.

For **persistent storage**, EKS can use these as storage providers:

- **EBS**
- **EFS**
- **FSx**

### Context bar (title)

**Elastic Kubernetes Service 101 (EKS)** — a simple, conceptual EKS deployment. Source: learn.cantrill.io.

### Main / middle objects

The deployment conceptually spans **two VPCs**:

**1. AWS-Managed VPC (top, purple-bordered box, K8s logo inside)**

- This is where the **EKS control plane** runs.
- Labelled **"Control Plane — Managed & Multi AZ"** (the dashed vertical lanes inside the box represent the multiple AZs it spans).
- The control plane is **not** in your account's VPC — AWS owns and runs this VPC.

**2. Animals4life Customer VPC (right, purple-bordered box)**

- Contains the **Worker Nodes (EC2)** — the three computer/instance icons sitting in dashed AZ lanes.
- If you use **EC2 worker nodes**, they're deployed **here**, in _your_ VPC.

**The connections between the two VPCs:**

- **Green solid line — "Control Plane: ENIs injected into Customer VPC."** The control plane reaches the worker nodes via **Elastic Network Interfaces** that AWS **injects into the customer VPC**. The branching green lines into the three nodes represent this.
- **Green/red double-headed arrow — "kube-api traffic."** The **kubelet** service on each worker node connects to the control plane. This communication path can be **either** the injected ENIs **or** a **public control plane endpoint**.
- **Red dotted curved line + red arrow on the left — "EKS Admin via public endpoint."** The laptop (admin) on the far left reaches the control plane through the **public endpoint** for administration. The load-balancer-style icon next to the laptop represents this entry path.

**Bottom-centre — Service Consumer (monitor icon)**

- The **green arrow** from the worker nodes' load balancer icon flows to the Service Consumer.
- Consumption of EKS services happens via **ingress configurations**, which **start from the customer VPC** and serve the end consumer.

### Footer / takeaways from the diagram

- Control plane = AWS-managed VPC, multi-AZ.
- Worker nodes (if EC2) = customer VPC.
- Two communication paths: **injected ENIs** and the **public endpoint**.
- **Admin** uses the public endpoint; **service consumption** flows out via ingress from the customer VPC.

## Exam-Focused Recap

- EKS = **managed Kubernetes**, **same K8s as everywhere**, **cloud-agnostic** → pick it to avoid lock-in or to bring existing K8s workloads.
- **Control plane + etcd**: AWS-managed, multi-AZ.
- **Integrations:** ECR, ELB, IAM, VPC.
- **Nodes:** self-managed EC2 · managed node groups (EC2) · Fargate (serverless, via Fargate profiles).
- **Special capability needs** (Windows / GPU / Inferentia / Bottlerocket / Outposts / Local Zones) constrain your node choice — **check support first**.
- **Persistent storage:** EBS, EFS, FSx.
- **Architecture:** control plane in AWS-managed VPC; EC2 workers in customer VPC; connectivity via **injected ENIs** or **public endpoint**.
