## 1. What KMS Is

- **Regional & public service** — every region has its own isolated KMS endpoint. A key created in `us-west-2` exists only in `us-west-2`.
- **Create, store, and manage keys** on AWS's behalf — KMS is the encryption root of trust used by almost every other AWS service that offers encryption (S3, EBS, RDS, Secrets Manager, etc.).
- Supports both **symmetric** and **asymmetric** keys.
- Performs **cryptographic operations** itself: `Encrypt`, `Decrypt`, `Sign`, `Verify`, `GenerateDataKey`, etc.
- **Keys never leave KMS.** Backing key material is generated inside, used inside, and destroyed inside.
- Provides **FIPS 140-2 (Level 2)** compliance — relevant for regulated workloads. (Some operations meet L3 inside the HSMs, but the service-level claim is L2.)

---

## 2. KMS Keys (formerly "CMKs")

- A KMS Key is a **logical container** holding metadata: **ID, creation date, key policy, description, and state**.
- That logical key is **backed by physical key material** — the actual bytes used for crypto. The two are conceptually distinct.
- Key material is either:
  - **Generated** by KMS (the default), or
  - **Imported** (BYOK — bring your own key material).
- A KMS Key can **directly encrypt/decrypt up to 4 KB of data per call**. Anything larger needs **Data Encryption Keys** (see §5).

### The basic encrypt/decrypt flow (slide diagram)

![[KMS-create-encrypt-decrypt-processes.png]]

Key takeaways from the diagram:

- The plaintext key never leaves KMS — only the locked/encrypted artifacts cross the KMS boundary.
- The caller never sees the raw key — they send data **in**, get ciphertext **out**.
- `Encrypt` and `Decrypt` are separate API calls against the same KMS Key ID.

## 3. CLI Example — Direct Encrypt of a Small File

A hands-on demonstration of the basic `Encrypt` operation against a KMS Key:

![[KMS-cli.png]]

```bash
aws kms encrypt \
    --key-id alias/catrobot \
    --plaintext fileb://battleplans.txt \
    --output text \
    --query CiphertextBlob \
    | base64 --decode > not_battleplans.enc
```

What each piece does:

| Flag / Step                            | Purpose                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------- |
| `--key-id alias/catrobot`              | Reference the KMS Key by **alias** (friendlier than the raw UUID — and re-pointable). |
| `--plaintext fileb://battleplans.txt`  | `fileb://` reads the file as **raw binary** (use `file://` for text).                 |
| `--output text --query CiphertextBlob` | Strip the JSON envelope and emit only the ciphertext field.                           |
| `\| base64 --decode`                   | KMS returns ciphertext **base64-encoded** by default; decode back to raw bytes.       |
| `> not_battleplans.enc`                | Write the encrypted blob to disk.                                                     |

> Decrypt symmetry: `aws kms decrypt --ciphertext-blob fileb://not_battleplans.enc --output text --query Plaintext | base64 --decode > battleplans.txt`. Notice **you don't specify a `--key-id` on decrypt** for symmetric keys — KMS reads the Key ID from metadata embedded in the ciphertext blob.
> Reminder: this only works because `battleplans.txt` is **≤ 4 KB**. For anything larger, see §5.

## 4. The 4 KB Limit and Why DEKs Exist

KMS's direct `Encrypt`/`Decrypt` operations are capped at **4 KB** of payload. You cannot send a 1 GB file through `Encrypt`. The pattern AWS uses everywhere to get around this is **envelope encryption** with Data Encryption Keys.

---

## 5. Data Encryption Keys (DEKs)

DEKs are created via **`GenerateDataKey`** against a KMS Key. They are the mechanism for encrypting data **larger than 4 KB**.

![[KMS-DEK-handling-gte4KB.png]]

### The envelope encryption flow

1. Call `GenerateDataKey` on a KMS Key.
2. KMS returns **two versions of the same DEK**:
   - **Plaintext version** — the actual DEK bytes you'll use right now.
   - **Ciphertext version** — the DEK encrypted under the KMS Key.
3. **Encrypt your data locally** using the plaintext DEK (AES, etc. — done outside KMS).
4. **Discard the plaintext DEK** from memory immediately after use.
5. **Store the encrypted (ciphertext) DEK alongside the encrypted data**.

To decrypt later:

- Send the ciphertext DEK to KMS → `Decrypt` → plaintext DEK back in memory.
- Use it to decrypt the data locally.
- Discard plaintext DEK again.

> KMS itself **does not store DEKs** — it only generates them. Storing the encrypted DEK with the ciphertext is the caller's responsibility. This is why services like S3 SSE-KMS embed the encrypted DEK in object metadata.

## 6. Key Concepts

| Concept                   | Notes                                                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Region isolation**      | KMS Keys are scoped to a single region and never leave it.                                                                                                                                       |
| **Multi-region keys**     | Exist as a separate feature (replica keys across regions) — covered in a different video.                                                                                                        |
| **AWS Owned keys**        | Owned and used by AWS itself across many accounts. You never see them. No cost, no control.                                                                                                      |
| **Customer Owned keys**   | Keys that live inside *your* account. Two sub-types ↓                                                                                                                                            |
| **AWS Managed keys**      | Customer-owned, but AWS creates and rotates them on your behalf (e.g. `aws/s3`, `aws/rds`). Limited configurability.                                                                             |
| **Customer Managed keys** | You create, configure, and control them — **more configurable**: custom key policy, manual rotation control, can be disabled/deleted, can have grants and aliases.                               |
| **Rotation**              | KMS Keys support rotation. When rotated, a **new backing key** is generated; the **previous backing keys are retained** so old ciphertexts can still be decrypted under the same logical key ID. |
| **Aliases**               | Friendly names (e.g. `alias/unitpulse-prod-s3`) that point to a Key ID. Useful for portability — you can repoint an alias at a new key without changing callers.                                 |

## 7. Key Policies and Security

KMS has **three layers of access control**, and they work *together*:

![[KMS-key-policies.png]]

### 7.1 Key Policies (resource policy)

- Every KMS Key has **one key policy** — it is mandatory, not optional.
- A key policy is a **resource policy** attached to the key itself.
- Unlike S3 buckets, **IAM permissions alone are not enough**. The key policy must explicitly trust the account before IAM policies in that account can grant access to the key.

Minimal "trust my own account" key policy statement (from the slide):

```json
{
  "Sid": "Enable IAM User Permissions",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  "Action": "kms:*",
  "Resource": "*"
}
```

This says: *"Allow the account `111122223333` (via IAM) to govern this key."* Once this exists, IAM policies in that account can grant `kms:Encrypt`, `kms:Decrypt`, etc.

### 7.2 Key Policies + IAM Policies

- After the key policy delegates to the account root, normal IAM identity policies decide which principals get which KMS actions.
- Example IAM policy granting encrypt/decrypt on any key in the account:

```json
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Action": ["kms:Encrypt", "kms:Decrypt"],
    "Resource": ["arn:aws:kms:*:111122223333:key/*"]
  }
}
```

### 7.3 Key Policies + Grants

- **Grants** are a third mechanism — temporary, programmatic permission delegations created via the KMS API.
- Used heavily by AWS services that need short-lived, scoped access to use a key on behalf of a principal (e.g., EBS attaching an encrypted volume).

> Mental model: **key policy is the gate**, **IAM is the in-account rulebook**, **grants are temporary side passes**.

---

## Quick reference — what to remember for the exam

- KMS = regional, FIPS 140-2 L2, keys never leave the service.
- Direct encrypt/decrypt is **4 KB max** → larger payloads use **`GenerateDataKey`** + envelope encryption.
- `GenerateDataKey` returns **plaintext + ciphertext** versions of the DEK; you use plaintext, then discard, then store ciphertext with the data.
- **AWS Owned** vs **AWS Managed** vs **Customer Managed** — only Customer Managed gives full control (policies, rotation, aliases, grants, deletion).
- Rotation creates new backing key material; old backing keys are kept so old ciphertexts stay decryptable.
- **Every key has a key policy, and it is required** — IAM alone cannot grant access to a KMS key.
- Three access layers: **Key Policy + IAM Policies + Grants**.
