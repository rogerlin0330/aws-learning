# Elastic Container Registry (ECR)

> **In one line:** ECR is AWS's managed container image registry — think _Docker Hub, but for AWS_. It hosts and manages container images for use with Docker, ECS, EKS, and other container applications.

---

## 1. What ECR Is

A **managed container image registry service**. AWS hosts and manages your container images so other container services (ECS, EKS, plain Docker) can pull and run them.

---

## 2. Structure / Hierarchy

ECR follows a clean top-down structure. Think of it like a source-control system (Git/GitHub):

```
Registry (public or private)
  └── Repository (many per registry — like a Git repo)
        └── Container Image (many per repository)
              └── Tag (many per image — must be unique within the repo)
```

|Level|Notes|
|---|---|
|**Registry**|Each AWS account gets **one public** and **one private** registry. Top-level structure.|
|**Repository**|Many per registry. Analogous to repos in Git/GitHub.|
|**Image**|Many per repository.|
|**Tag**|Many per image. **Tags must be unique within the repository.**|

> 🎯 **Exam angle:** Remember each account has **one of each** registry type (one public + one private). Repos → images → tags is the nesting order.

---

## 3. Security Architecture: Public vs Private

|Registry Type|Read (pull)|Read-Write (push)|
|---|---|---|
|**Public**|Anyone — read-only, no permissions needed|Permissions required|
|**Private**|Permissions required|Permissions required|

In plain terms:

- **Public registry** → anyone can **pull**; pushing needs permissions.
- **Private registry** → permissions required for **any** operation (pull _and_ push).

> 🎯 **Exam trigger keywords:** "anyone can pull" / "open read access" → **public**. "permissions required for all operations" → **private**.

---

## 4. Benefits & Features

|Feature|Detail|
|---|---|
|**IAM integration**|All access permissions controlled via IAM.|
|**Security scanning**|Two flavors: **Basic** and **Enhanced**. Enhanced uses **Amazon Inspector**, scans both the **OS** and **software packages**, and works on a **layer-by-layer** basis.|
|**CloudWatch metrics**|Near real-time metrics for authentication, push, and pull operations.|
|**CloudTrail**|Logs all **API actions**.|
|**EventBridge**|Generates **events** for event-driven workflows involving container images.|
|**Replication**|Both **cross-region** and **cross-account**.|

> 🎯 **Exam angle — match the service to the job:**
> 
> - Vulnerability/CVE scanning of images, OS + packages, layer-by-layer → **Enhanced scanning (Inspector)**
> - Metrics on pull/push/auth → **CloudWatch**
> - Audit trail of API calls → **CloudTrail**
> - Trigger an automated workflow when an image changes → **EventBridge**
> - Get images into another region or account → **Replication (cross-region / cross-account)**

> ⚠️ **Trap:** Don't confuse **Basic** vs **Enhanced** scanning. Only **Enhanced** uses **Inspector** and adds OS + software package, layer-by-layer scanning. Basic is the lighter, default-style option.

---

## 5. Exam-Focused Recap

- ECR = **managed container image registry** ("Docker Hub for AWS").
- Hierarchy: **Registry → Repository → Image → Tag**; tags unique per repo.
- Each account: **one public + one private** registry.
- **Public** = anyone pulls, push needs permissions. **Private** = permissions for everything.
- **IAM** controls all permissions.
- **Enhanced scanning → Inspector** (OS + packages, layer-by-layer); Basic is the simpler option.
- Observability: **CloudWatch** (metrics), **CloudTrail** (API logs), **EventBridge** (events).
- **Replication** is **cross-region AND cross-account**.
