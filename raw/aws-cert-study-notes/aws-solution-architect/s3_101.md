## Foundational Concepts

**S3 is a global storage platform built on regional infrastructure.** It runs from every AWS region, is accessible from anywhere with an internet connection (it lives in the AWS public zone), but each piece of data has a **home region** where it sits at rest. Data **never leaves that region** unless you explicitly configure it to (e.g., cross-region replication).

S3 delivers two primary primitives:

- **Objects** — the data itself (files, images, video, datasets, backups, logs)
- **Buckets** — region-scoped containers that hold objects

**Resilience model:**

- **Regionally resilient** — objects are replicated across AZs within the home region, so S3 can survive an AZ failure transparently.
- **Blast radius = the region.** A catastrophic regional failure (natural disaster, large-scale corruption) is contained to that region. Cross-region replication is opt-in.

**Access methods:** Console (GUI), AWS CLI, AWS SDKs/APIs, and direct HTTP(S).

**Mental model:** S3 should be your **default storage choice in AWS** unless a specific requirement (file system semantics, block-level access, sub-millisecond latency) rules it out. Nearly every other AWS service integrates with S3 as either an input source or output sink.

## Mechanics

### Objects

An object has two essential components plus metadata:

|Component|Description|
|---|---|
|**Key**|The object's name — uniquely identifies the object _within a bucket_. Combined with the bucket, this uniquely addresses the object globally.|
|**Value**|The actual data (the bytes). Size range: **0 bytes → 5 TB**.|
|Version ID|Identifier when versioning is enabled (covered later).|
|Metadata|System and user-defined metadata.|
|Access control|Per-object ACLs (legacy mechanism; bucket policies preferred).|
|Sub-resources|Additional per-object configuration.|

The 0 B → 5 TB range is one of the main reasons S3 scales to so many use cases — from empty marker objects to multi-terabyte media files.

### Buckets

A bucket is a regional container. Creation pins the bucket to one region, which gives:

- **Data sovereignty** — you control which jurisdiction's laws apply by choosing the region.
- **Predictable blast radius** — failure containment is regional.

**Naming rules** (these matter for the exam _and_ for real provisioning errors):

- **Globally unique** across all AWS accounts and all regions — not just unique within your account.
- 3–63 characters
- Lowercase letters, numbers, and hyphens only — **no underscores**
- Must start with a lowercase letter or number
- Cannot be formatted like an IP address (e.g., `10.0.0.1` is invalid)

**Bucket limits:**

|Limit|Value|
|---|---|
|Soft limit (default)|**100 buckets per account**|
|Hard limit (via support request)|**1,000 buckets per account**|
|Objects per bucket|**Unlimited**|
|Object size|0 B – 5 TB|

The 100/1,000 cap is **per account, not per region** — an architectural constraint, not arbitrary trivia (see decision guidance below).

### Flat Structure — No True Folders

This is the most important conceptual point in the lesson and the focus of the diagram below:

![[s3-101.png]]

**S3 is object storage with a flat namespace.** Every object in a bucket lives at the same level. There are no real directories.

When you see something that looks like a folder in the console — e.g., an `old/` folder containing `Koala1.jpg` — what actually exists is three objects with these keys:

```
/old/Koala1.jpg
/old/Koala2.jpg
/old/Koala3.jpg
```

The `/old/` portion is just part of the object key. The console parses these keys and **presents** a folder UI, but no folder entity exists in the underlying storage. These pseudo-folders are called **prefixes** because they prefix the object key.

**Why this matters:**

- Listing objects by prefix is how you simulate "browse a folder."
- Permissions, lifecycle rules, and replication rules often target prefixes.
- It explains why S3 is not a filesystem — there is no rename-a-directory operation; "moving" a folder means rewriting every object's key.

## What S3 Is Good For (and Not)

S3 is **object storage**, distinct from **file storage** and **block storage**. The storage type determines what workloads fit:

|Storage type|Access pattern|AWS example|S3 fit?|
|---|---|---|---|
|**Object**|Whole-entity reads/writes via API (PUT/GET an entire object)|S3|✅ This is S3|
|**File**|Network file system semantics (NFS, SMB), shared mount, partial reads|EFS, FSx|❌ Not S3|
|**Block**|Mounted as a volume/disk, single-instance attach, partial reads/writes|EBS|❌ Not S3|

**Good fits for S3:**

- Large-scale data storage and distribution (media, backups, datasets, IoT telemetry)
- Static asset offload (images, video, audio from a blog or web app) — shrinks compute footprint
- Input source or output destination for other AWS services (Athena, Glue, EMR, SageMaker, CloudTrail, etc.)
- Multi-reader scenarios (millions of concurrent users)

**Not a fit for S3:**

- Mounted drives on EC2 / Windows file shares → use **EBS** (block) or **EFS / FSx** (file)
- Workloads needing partial-byte writes to a single object with low latency
- Anything requiring true POSIX filesystem semantics

## Decision Guidance

**"Should I use one bucket per user?"** — Almost certainly no. With a 1,000-bucket hard ceiling per account, any system with ~100+ users that uses bucket-per-user will not scale. The standard pattern is **one bucket, partitioned by prefix per user** (e.g., `s3://app-data/users/<user-id>/...`).

**"Where should the output of \<AWS service\> go?"** — Default to S3 unless the requirement explicitly demands file or block semantics. In the exam, when multiple storage options appear, **S3 is the default correct answer** for bulk service input/output.

**"Object storage vs file vs block?"** — Ask how the workload accesses the data:

- Whole-object reads/writes over HTTP/API → S3
- Network file share, multi-instance shared mount → EFS/FSx
- Single-instance disk volume, mounted at the OS → EBS

**"Can I mount an S3 bucket as a drive?"** — Not natively (third-party tools and Mountpoint for S3 exist but with caveats). If the requirement says "mount" or "drive letter," it's not S3.

## Exam Cheat Sheet

|Keyword / scenario in question|Answer|
|---|---|
|"Globally unique" bucket name|✅ S3 — bucket names are unique across **all accounts and regions**|
|Bucket name with underscore, uppercase, or `1.1.1.1` format|❌ Invalid bucket name|
|Max object size|**5 TB**|
|Min object size|**0 bytes**|
|Max objects per bucket|**Unlimited**|
|Default bucket limit per account|**100** (soft)|
|Hard bucket limit per account|**1,000**|
|"Thousands of users, one bucket each"|❌ Use **one bucket + prefixes per user** instead|
|"Mount as a drive / volume"|❌ Not S3 — use **EBS** (block) or **EFS** (file)|
|"Network file share for Windows / Linux"|❌ Not S3 — use **FSx** or **EFS**|
|"Default storage for AWS service input/output"|✅ S3|
|"Large-scale data distribution to many users"|✅ S3|
|"Offload static assets from EC2"|✅ S3|
|"Folder" in S3|Actually a **prefix** — flat structure underneath|
|Data leaves the region automatically?|❌ No — only if you configure replication|
|Blast radius of S3 bucket|**The region** it was created in|
|Resilience model|Replicated across **AZs within the region**|

## Key Object/Bucket Components — Quick Reference

```
Object:
├── Key            ← the name (e.g., "/old/Koala1.jpg")
├── Value          ← the data (0 B – 5 TB)
├── Version ID     ← (when versioning enabled)
├── Metadata       ← system + user-defined
├── ACL            ← legacy per-object permissions
└── Sub-resources  ← additional per-object config

Bucket:
├── Name           ← globally unique, 3–63 chars, lowercase + digits + hyphens
├── Region         ← chosen at creation; pins data sovereignty
├── Objects        ← unlimited count, flat namespace
└── Configuration  ← policies, lifecycle, replication, versioning, encryption, etc.
                    ← (most permissions/options are set at the BUCKET level)
```
