## [2026-05-20] fix | S3 Bucket Keys — model the many-bucket-level-keys-accumulate-over-time reality

Substantive correction to the **S3 Bucket Keys** subsection of `services/s3.md`. The previous draft implicitly treated each bucket as having **one** bucket-level key, with "ciphertext form of the bucket-level key" used as a singular noun phrase throughout. A user follow-up made the obvious-in-retrospect point: since bucket-level keys have a finite active-for-encryption lifetime and S3 rotates them periodically, there must be **many** ciphertext forms accumulating in S3's durable state over time — one per historical bucket-level key — each needed indefinitely to decrypt the objects it originally wrapped.

Updates across the section:

1. **Storage table** — replaced the singular "Ciphertext form of the bucket-level key" row with `Map of bucket-level-key-ID → ciphertext form of that bucket-level key`, with a one-entry-per-historical-key explanation. Added a warning callout right under the table making the many-keys-accumulate point explicit and clarifying that the "ciphertext form of the bucket-level key" phrasing used throughout is always *that-specific-one*, never *the* one.
2. **Encryption walk step 3** — instead of "persists the ciphertext bucket-level key to durable state", now says "adds a new entry to the durable map of bucket-level keys (`bucket-level-key-ID → ciphertext form`); the map already contains entries for every previously-used bucket-level key in this bucket; this is a new entry appended to it."
3. **Encryption walk step 7** — object metadata now explicitly includes the **bucket-level-key-ID** (the lookup key future GETs use to find the right durable-map entry), in addition to the ciphertext form of the per-object DEK.
4. **Decryption walk steps 1–2** — step 1 reads the bucket-level-key-ID from object metadata; step 2 uses that ID to look up the correct entry in the durable map (which "may contain many entries — one per historical bucket-level key — and this lookup picks out the exact one that matches the object's ID").
5. **"What expires" subsection** — full rewrite. The previous "two lifetimes (cache vs cryptographic)" framing was muddled. Replaced with the cleaner **two-phases-per-bucket-level-key** model: **Active for encryption** (limited window; this is the *current* bucket-level key for new PUTs) → **Retired but recoverable** (effectively forever; ciphertext form stays in the durable map and is used on demand by GETs against old objects). "Expires" now correctly refers to the active→retired transition, not destruction. Added an ASCII timeline diagram showing successive bucket-level keys (bk-001, bk-002, bk-003, …) each in active-then-retired-but-recoverable mode, and a monotonically-growing durable map. Clarified that the cache (in-memory plaintext) is **orthogonal** to the active/retired phase — any bucket-level key can be cached or not at any moment, and cold-cache decryption pays one KMS `Decrypt` regardless of whether the bucket-level key is currently active or long retired. Crypto-shred via CMK deletion remains the only path to true unrecoverability.

This fixes a misconception I'd been propagating since the original ingest — implicitly suggesting that "the bucket-level key expires" meant only cache eviction, which papered over the fact that the bucket-level key itself rotates (active-for-encryption) while the **old keys' ciphertext forms accumulate in durable state**.

## [2026-05-20] fix | S3 Bucket Keys — correct the "PUT can call Decrypt" overclaim

Fixed an overclaim in the **S3 Bucket Keys** subsection of `services/s3.md`. A previous draft of the encryption walk said S3 might call either `GenerateDataKey` *or* `Decrypt` on a cold-cache PUT — the latter only if a bucket-level key already existed in durable state and S3 was "re-warming" it. That goes beyond what AWS documents. The clean, defensible model — and the one consistent with the verbs' semantics — is:

- **Cold PUT** (encrypt) → `GenerateDataKey` (mints fresh key material)
- **Cold GET** (decrypt) → `Decrypt` (recovers existing key material from its ciphertext form)

`GenerateDataKey` is for creating new material; `Decrypt` is for recovering existing material. PUTs only ever call `GenerateDataKey`; GETs only ever call `Decrypt`. Rewrote step 2 of the encryption walk to drop the "or `Decrypt`" branch and the sub-bullet asymmetry between the two API outputs. Replaced the three-row "Which KMS API gets called" table with a cleaner two-row table keyed on operation direction (encrypt vs decrypt) plus a one-line intuition statement. Left the "AWS docs use 'fetched' loosely" note in place — still true at the bucket-level-key-fetch granularity — but it no longer suggests `Decrypt` is part of the PUT path.

## [2026-05-17] update | s3.md — clarify Block Public Access semantics

Added a warning callout in the Block Public Access section emphasizing that disabling BPA is not equivalent to making a bucket public. The two switches are independent: a bucket stays private by default, and turning BPA off merely removes the failsafe — public access still requires a bucket policy (or ACL) granting `Principal: "*"`. Conversely, leaving BPA on while attaching a public policy yields 403. Both a grant and the absence of the override must line up.
