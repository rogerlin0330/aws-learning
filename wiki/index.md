- [EC2](services/ec2.md) — Virtual compute; IaaS foundations (instance = OS + allocated resources, private-by-default in a VPC subnet, AZ-resilient not fault-tolerant, customizable at launch, shared responsibility line at the hypervisor), hosts vs instances (host = physical AWS-managed hardware in one AZ; enforce **IMDSv2** session-token handshake via `HttpTokens=required`), AMI as launch template (a **logical container** holding AMI ID + permissions + block device mapping pointing at EBS snapshots — no volume data in the AMI itself; sources = AWS / Community / Marketplace with Marketplace adding a per-hour license charge on top of the instance rate; permission modes **Private** default / Public / Explicit named accounts; four-phase lifecycle Launch → Configure → Create Image → Launch; region-specific but deployable to **any AZ in the region**; **cannot be edited** — launch, modify, recreate; can be copied across regions with `copy-image`, permissions reset to Private; billed on **EBS snapshot used data**, not the container or the volume's allocated size; **AMI baking** = configure once, capture, stamp out many), connecting to instances (Linux SSH/22 direct public-key auth; Windows RDP/3389 with private key used to decrypt the local Administrator password first), SSH key-pair mechanics (private key downloads once, AWS keeps the public key), when to use EC2 (default compute; long-running 24/7, OS-specific workloads, monolithic stacks, on-prem VM migrations, traditional DR — deviate to Lambda/Fargate/Beanstalk only when a specific requirement justifies it), instance types (5 categories: General Purpose / Compute Optimized / Memory Optimized / Accelerated Computing / Storage Optimized; type name decode: family+generation+capability-letters+size; burstable T3 vs steady-state M5; Graviton ARM families A1/M6g), bootstrapping (self-configure at launch via **user data** served over IMDS at `/latest/user-data/`; runs **once** as root, **opaque** to EC2 so a failed bootstrap still passes status checks = silent bad config; not a secret store — no long-term creds; 16 KB cap; console auto-base64s but CloudFormation needs `Fn::Base64`; diagnose via `/var/log/cloud-init-output.log`; procedural one-shot vs cfn-init desired-state), instance roles & instance profiles (instance role = IAM role trusting `ec2.amazonaws.com` so an app reaches other AWS services with **no stored access keys**; temporary credentials delivered via **IMDS** at `iam/security-credentials/<role-name>` and **auto-renewed by EC2 + STS**; instance profile credentials are **last** in the CLI provider chain so the CLI just works — but env vars / `~/.aws/credentials` **silently shadow** the role; mnemonic **RPM** = Role-Profile-Metadata), placement groups (influence physical placement on hosts; **Cluster** = same rack often same host, 10 Gbps single-stream vs 5 normal, locked to the AZ of the first launch, needs supported type + enhanced networking, little resilience, HPC; - [ELB](services/elb.md) — Elastic Load Balancer; family split (CLB v1 legacy — never for new deployments; ALB true-L7 HTTP/HTTPS/WebSocket; NLB L4 TCP/TLS/UDP; GWLB L3/GENEVE noted), the ALB-vs-NLB protocol decision as the core exam skill, nodes-not-a-box architecture (1+ auto-scaling HA nodes per chosen subnet, one subnet per AZ, single A record resolving to all nodes, DNS responses statistically distribute clients across nodes), internet-facing vs internal (node IP addressing is the **only** difference; egress patch-download AV/IPS supply-chain defence) and the health-checked-fleet HA argument; L3-vs-L3/L4 and 5/3/2-tuple course-vs-reality flags)
- [EC2 Auto Scaling](services/ec2-auto-scaling.md) — Auto Scaling groups (the service is EC2 Auto Scaling; the ASG is its resource — distinct from Application Auto Scaling and scaling plans); min/desired/max with clamping as a documented guarantee, ASG controls when/where vs launch template controls what, Multi-AZ subnet placement with best-effort AZ balance, scaling methods (manual as cost-control pin; scheduled for predictable patterns; dynamic: simple / step / target tracking / SQS worker-pool on `ApproximateNumberOfMessagesVisible`), target tracking's 4 predefined metrics (incl. `ALBRequestCountPerTarget`, ALB-only) with AWS-managed alarms ("who owns the alarm" discriminator), the target-tracking-first-then-step-then-simple recommendation hierarchy with simple scaling's cooldown-blocking flaw, cooldown (simple-only, 300 s default) vs default instance warmup (target tracking/step), health checks (EC2 status vs application-aware ELB checks; DB-dependency fleet-churn gotcha), self-healing + the min = desired = max = 1 cheap-HA pattern, automatic target-group registration, lifecycle hooks (Pending/Terminating Wait + Proceed state machine, 3600 s default timeout vs 7200 s heartbeat max vs 48 h/100× global cap, `DefaultResult` ABANDON never rescues, `CompleteLifecycleAction` / `RecordLifecycleActionHeartbeat`, SNS/SQS/EventBridge targets, warm pools note), suspendable scaling processes + Standby, free (pay only for provisioned resources)
- [ECS](services/ecs.md) — Managed container orchestration (AWS-proprietary); cluster/service/task/container hierarchy, task definitions vs container definitions, task role vs execution role, services for desired-count HA and load balancing, registries/ECR, EC2 launch type vs Fargate launch type, capacity providers, Fargate ENI/VPC networking, EC2-vs-Fargate choice heuristics, and ECS-vs-EKS positioning

- [EKS](services/eks.md) — AWS-managed [Kubernetes](concepts/kubernetes.md); same cloud-agnostic Kubernetes with AWS running the control plane + etcd (both multi-AZ), deployment modes (AWS / Outposts / EKS Anywhere / EKS Distro), cluster endpoint access (public/private/both), integrations (ECR/ELB/IAM/VPC), node options (self-managed EC2 / managed node groups / Fargate via Fargate profiles), capability-support caveats (Windows/GPU/Inferentia/Bottlerocket/Outposts/Local Zones), persistent storage providers (EBS/EFS/FSx), two-VPC architecture (control plane in AWS-managed VPC, EC2 workers in customer VPC, connected via injected ENIs or public endpoint), per-cluster control-plane fee, and ECS-vs-EKS decision framing
- [Lambda](services/lambda.md) — Function as a Service (FaaS); the serverless/event-driven compute primitive that bills only for execution duration; function = code + runtime + config run in a purpose-built **execution context**; resource model (memory 128–10240 MB in 1 MB steps directly set, **1769 MB = 1 vCPU** indirect, ~6 vCPU ceiling, `/tmp` 512 MB–10 GB ephemeral, 50 MB-zipped/250 MB-unzipped package or 10 GB container image, **900 s / 15-min hard timeout** — beyond it use Step Functions); runtimes (Python/Node/Ruby/Java/Go/C#, Rust via layers) with the **"Docker" = NOT Lambda** exam signal (bare Docker means ECS; Lambda container images run *inside* Lambda); statelessness (assume a fresh context every time, never depend on reuse); **two networking modes** (public default reaches public AWS + internet but not VPC resources; VPC mode obeys all normal VPC rules, needs gateway endpoint or NAT+IGW for outside access, and the **execution role needs EC2 network permissions** to create ENIs — old one-ENI-per-function-per-invocation model superseded by shared Hyperplane ENI per unique SG+subnet combo, ~90 s setup, no per-invocation delay); **two-part security model** ([resource policy](concepts/resource-vs-identity-policies.md) = who can invoke, like an S3 bucket policy; **execution role** = what the function can do, like an [EC2 instance role](services/ec2.md#instance-roles--instance-profiles); no-CloudWatch-Logs = missing execution-role permission); **three invocation types** (sync = client retries; async = Lambda retries 0–2, **requires idempotency**, DLQ + success/failure destinations; **event source mapping** polls Kinesis/DynamoDB Streams/SQS/MSK and reads via the **execution role's source permissions** even though the code never calls the source); **versions** (immutable, own ARN) vs `$LATEST`/**aliases** (mutable); **cold start** (~100 ms full context build) vs **warm start** (~1–2 ms reuse), **provisioned concurrency**, and declare-reusable-objects-outside-the-handler optimization ([RDS Proxy](services/rds-proxy.md) for connection reuse)
- [S3](services/s3.md) — Object storage; foundations (global platform on regional infrastructure, multi-AZ resilience with per-region blast radius, objects + buckets primitives, 0 B–5 TB object size, unlimited objects, 10,000 default general-purpose buckets per account with adjustable quota, classic shared-global bucket namespace plus newer account-regional namespace option, flat namespace for general-purpose buckets where "folders" are key prefixes, object vs file vs block storage decision against EFS / FSx / EBS), bucket policies, ACLs (legacy), Block Public Access, cross-account & anonymous access, pre-signed URLs (time-limited single-object access; IAM user vs role; permissions evaluated at use time), versioning + MFA Delete, Object Lock (WORM immutability for object versions; Compliance vs Governance retention; Legal Hold; bucket-level permanence — auto-enables versioning and cannot be disabled; can be enabled on existing buckets with console/CLI/API/SDK), object encryption (SSE-S3 / SSE-KMS / SSE-C / CSE) + S3 Bucket Keys, multipart upload + Transfer Acceleration, storage classes (Standard / IA / One Zone-IA / Glacier tiers / Intelligent-Tiering), lifecycle configuration (transitions + expiration; waterfall rules; 30-day Standard minimum; single-rule IA-to-Glacier gap), replication (CRR / SRR; same-account vs cross-account; RTC 15-min SLA; what's not replicated), server-side filtering (S3 Select / Glacier Select; legacy/current-for-existing-customers row/column filter pushed into the service; per-object only — Athena for multi-object), event notifications (Lambda / SQS / SNS destinations; Create/Delete/Restore/Replicate event types; destination resource policy must trust `s3.amazonaws.com`; EventBridge as the broader alternative), access logging (async best-effort request-level audit log; same-account same-region source → target bucket; - [RDS](services/rds.md) — Managed relational database **server** (not "database as a service" — one instance hosts multiple databases); **databases on EC2** decision (always architecturally worse + single-AZ by nature, but the right answer for an unsupported engine/version, a specific OS+DB combo, an AWS-unsupported replication architecture, or genuine OS/root access — often softened by RDS Custom); managed surface (no SSH/OS access, engines Db2/MariaDB/MySQL/Oracle/PostgreSQL/SQL Server, **Aurora is a separate shared-cluster-storage product**); **RDS Custom** (the middle ground between managed RDS and DB-on-EC2 — **SQL Server + Oracle only**, OS/engine access via SSH/RDP/Session Manager, EC2/EBS/S3 resources **visible in your own account** unlike standard RDS's ENI-injection-only model, pause-customize-resume automation workflow, AWS-owns-hardware/customer-owns-optimization/everything-between-shared responsibility split); architecture (runs **inside a VPC**; **DB subnet group** = list of subnets RDS may use, required at launch, Multi-AZ picks primary+standby in different AZs at random; dedicated **EBS storage per instance** unlike Aurora; backups to AWS-managed S3); replication split (**standby = synchronous**, same-region/different-AZ, HA, not app-readable vs **read replica = asynchronous**, same- or cross-region, read scaling + DR, app-readable except Db2 standby replicas and Oracle mounted replicas are DR-only; SQL Server Multi-AZ backups briefly suspend I/O); **Multi-AZ deployments** (in-region HA only, not DR; two architectures — **instance mode** = 1 primary + 1 passive standby, synchronous storage-level replication, failover = DNS repoint 60–120s, all RDS engines; **cluster mode** = 1 writer + **2 readable** readers, semi-synchronous two-of-three quorum, transaction-log failover ~35s/25–75s, Graviton + local NVMe-flushed-to-EBS, **MySQL/PostgreSQL only**, Cluster/Reader/Instance endpoints with the instance endpoint test-only/no-failover; Single-AZ baseline = no standby, ~5min Recovery Point Objective (RPO)); **read replicas** (read-only async copies for **read scaling** + **cross-region DR**, distinct from the Multi-AZ standby in that they *are* app-readable but have their **own endpoint**, need **application changes**, and offer **no automatic failover** — only manual **promotion** to a standalone read/write instance; **5** per instance per the course vs **up to 15** in current AWS docs; **cascading** replicas allowed but **lag compounds**; cross-region link AWS-managed + encrypted in transit; near-zero **RPO/RTO** via promotion but **only for failure, never data corruption** since the replica holds the corrupted data — backups improve RPO, replicas improve RTO); **backups, snapshots & restore** (two mechanisms both stored in **AWS-managed S3** — regionally resilient, invisible in your own S3 console; **manual snapshots** = you-triggered, instance-level/all-DBs, **never expire**/survive instance deletion/manual-delete-only, 100/Region; **automated backups** = daily snapshot **+ transaction logs every 5 min**, retention **0–35 days** with 0 = disabled; **full-first-then-incremental shared by both** snapshot types; **PITR** = restore closest snapshot then replay logs to a chosen time at ~5-min RPO, **automated-backups-only**; "retain automated backups on delete" **still expires** — only a **final manual snapshot** is permanent; **cross-region backup replication** of snapshots + logs is **opt-in/extra cost**; a **restore always makes a new instance + new endpoint**, never overwrites, and restore time is your **Recovery Time Objective (RTO)** — backups improve RPO, **read replicas** improve RTO); **data security** (four concerns — authentication vs authorization, encryption in-transit vs at-rest; **in-transit** = per-user-mandatory SSL/TLS on all engines; **at-rest** two mechanisms by *who encrypts* — **KMS + EBS** host-side default on all engines, KMS key generates AES-256 DEKs covering storage/logs/snapshots/replicas with the **same key**, create-time-only + can't-remove + snapshot-copy-to-encrypt workaround vs engine-native **TDE** on **SQL Server/Oracle only**, with **Oracle + TDE + CloudHSM** as the no-AWS-in-the-chain-of-trust option; **IAM authentication** = 15-min `GenerateDBAuthToken` token instead of a DB password, **authentication-only never authorization** with the local DB user still governing permissions, TLS-mandatory, fresh-token-per-connection, EC2 instance-role-via-IMDS credentials-chain pattern, plus a PostgreSQL JDBC-pool walkthrough of the two wiring approaches — AWS Advanced JDBC Wrapper `iam` plugin vs a manual `RdsUtilities` token callback); cost model (resource-allocation like EC2, hourly **billed per second**, snapshot storage equal to DB storage free)
- [Aurora](services/aurora.md) — AWS-built relational engine, distinct from RDS; cluster (1 primary + up to 15 replicas that serve **reads and failover simultaneously**, any promotable, fast failover with no storage moves) on a **shared cluster volume** (6 copies across 3 AZs, synchronous storage-level replication with 4-of-6 quorum, no instance CPU cost, SSD-only, self-healing, max 128 TiB exam / 256 TiB current since Jul 2025); endpoints (cluster = primary R/W, reader = auto-updating load-balanced reads, custom, instance); billing (**Standard** = consumed GB-month + per-request I/O; **I/O-Optimized** = no separate read/write I/O charges; per-second compute with 10-min minimum, 100%-of-storage free backup allowance, no free tier; high-watermark billing on the exam vs dynamic resizing since 2020); **Backtrack** (in-place rewind, per-cluster opt-in, MySQL only) + **fast clones** (copy-on-write, stores only deltas); **Aurora serverless** (formerly Serverless v2; ACUs ≈ 2 GiB, min/max range, pause-to-zero = storage-only cost; v1 warm pool + proxy fleet retired Mar 2025; serverless = instance type in a normal cluster, 0.5-ACU steps, 0–256 ACUs, scale-to-zero since Nov 2024, Data API supported; RIs never apply — Database Savings Plans Dec 2025 do); **Global Database** (up to 5 exam / 10 current secondary regions each with up to 16 read-only replicas, storage-layer one-way ~1 s **async** cross-region replication vs synchronous in-region leg, RPO ~1 s failover / 0 switchover, RTO on the order of minutes, promote on disaster, DR + global reads); **multi-master** (retired with Aurora MySQL 5.6 EOL Feb 2023 — all-writer quorum commits, no cluster endpoint, app-managed load balancing/rerouting, fault tolerance not write scaling)
- [RDS Proxy](services/rds-proxy.md) — Fully managed database proxy for RDS and Aurora; **connection pooling + multiplexing** (many client-to-proxy connections onto fewer proxy-to-database connections, fixing "too many connections" on burstable t2/t3 instances and Lambda per-invocation connection overhead), **transparent failover** (clients hold a stable proxy endpoint and wait rather than error; proxy re-points its pool in the background, bypassing DNS caching for up to ~66% faster failover), fully managed/auto-scaling/HA-by-default, **VPC-only** (never public), engine support (RDS MySQL/MariaDB/PostgreSQL/SQL Server + Aurora MySQL/PostgreSQL — **no Oracle**, no self-managed EC2 databases), **Aurora read-only endpoints** (pool across replicas; plain-RDS proxies target the primary only), **session pinning** as the multiplexing gotcha (session state/prepared statements/temp tables/>16 KB statements disable it), **Secrets Manager required** for DB credentials even under IAM client auth, per-vCPU-hour pricing
- [DMS](services/dms.md) — Database Migration Service; managed data movement and replication for homogeneous and heterogeneous database migrations, DMS Standard replication instances vs DMS Serverless/DCUs, task modes (Full Load, Full Load + CDC, CDC Only), schema conversion split (DMS Schema Conversion or AWS SCT for engine changes), Snowball/S3 large-migration pattern, on-premises-to-on-premises unsupported, Fleet Advisor retired May 20, 2026

- [SQS](services/sqs.md) — Simple Queue Service; managed message queues, the public/regional/fully-managed decoupling primitive alongside [SNS](services/sns.md) and [EventBridge](services/eventbridge.md); **core loop** (send, poll, hide for the **visibility timeout** — default 30 s, range 0 s to 12 h — then explicitly delete, or the message reappears for another consumer, which is fault tolerance for free); `ChangeMessageVisibility` per-message extension and the 12-hour ceiling measured from the original receive; **delay queues** (`DelaySeconds`, hidden the moment the message is *added* rather than when it is *received*, 0 to 15 minutes, retroactive on FIFO but not standard) and **message timers** (per-message, unsupported on FIFO), with EventBridge Scheduler as the answer beyond 15 minutes; **Standard vs FIFO** (multi-lane vs single-lane highway; at-least-once + best-effort order + nearly unlimited TPS vs exactly-once-*into-the-queue* + strict order + `.fifo` suffix; 300 TPS unbatched / 3,000 batched by default, high throughput mode region-tiered up to 70,000 / 700,000 with partitions keyed on the hashed message group ID); the two FIFO mechanisms (`MessageDeduplicationId` 5-minute window at ingest vs `MessageGroupId` group hold at consume) and the **two layers of exclusivity** (visibility timeout on both types, group hold FIFO-only — which is *why* standard cannot preserve order); **"exactly-once" never means your code runs once** (consumer crash after work but before `DeleteMessage` redelivers on FIFO too, so consumers must be idempotent regardless); `MessageGroupId` on **standard** queues now enables **fair queues** (tenant fairness, not ordering); **dead-letter queues** (`ReceiveCount` exceeding `maxReceiveCount`, default 10; DLQ is an ordinary same-type/same-account/same-Region queue; one DLQ serves many sources; **enqueue timestamp is not reset** so DLQ retention must exceed the source's; redrive policy on the source vs redrive allow policy on the DLQ — `allowAll`/`byQueue` ≤10/`denyAll`; DLQ redrive back to source, FIFO-capable since Nov 2023); **long vs short polling** (`WaitTimeSeconds` 0 to 20 s; empty receives are billable); **billing per request in 64 KB chunks**, not per message; **1 MiB message ceiling since Aug 2025** (256 KB in course/exam material and still the SNS limit; S3 + pointer up to 2 GB beyond); **SNS fanout to multiple SQS queues** (one S3 event to one destination is why the pattern exists) and the **worker-pool** architecture (ASG on `ApproximateNumberOfMessagesVisible`, scaling to zero); retention 1 min to 14 days (default 4 days); 120,000 in-flight both types; encryption via KMS/SSE-SQS at rest and TLS in transit; cross-account via **queue policy**
- [Step Functions](services/step-functions.md) — Serverless orchestration; **state machines** (workflows) built from **states** that take data in, modify it, and pass it out; exists to work around two [Lambda](services/lambda.md) design decisions (**15-minute/900 s timeout** and **stateless execution environments**) — chaining Lambdas past 15 minutes is the wrong answer; **two workflow types fixed at creation and unchangeable** (Standard default = 1 year max, exactly-once, billed per state transition vs Express = 5 minutes max, at-least-once async/at-most-once sync, billed per execution + duration + memory); **eight current ASL state types** (Task, Choice, Parallel, Map, Pass, Wait, Succeed, Fail — the course lists seven, omitting Pass) split into flow control (Wait pauses for a duration or until a date/time, Choice branches on input, Parallel runs concurrent branches, Map repeats per list item, Succeed/Fail terminal) and the single work-performing **Task** state integrating Lambda/Batch/DynamoDB/ECS/SNS/SQS/Glue/SageMaker/EMR; **Step Functions coordinates, the integrated service computes**; definitions in **Amazon States Language (ASL), JSON-based**; permissions via an **IAM role assumed at runtime**; triggers include API Gateway, IoT rules, EventBridge, Lambda, or manual; **Pet Cuddle-O-Tron** walkthrough (S3 static site + API Gateway + API_Lambda starting the execution, Wait timer, Choice into EmailOnly/EmailAndSMS/SMSOnly Task branches, SES email and SNS SMS delivery) with the stateless Lambdas drawn *outside* the state-machine boundary
- [API Gateway](services/api-gateway.md) — Managed API creation/publishing/management; **English Excalidraw UML configuration diagram and separate runtime request-flow diagram with semantic colors** (general METHOD + URL template on both diagrams, default hostname → API, [stage/resource URL segments](services/api-gateway.md#reading-the-url-api-versus-stage-versus-resource), custom-domain mapping exceptions, REST API container versus individual endpoint terminology, API/Resource/Method, Method Request vs Integration Request, client GET vs Lambda integration POST, Stage/Deployment, reusable Authorizers, Usage Plans/API keys, and separate API/backend permissions); an **intermediary between clients and integrations** and the regional entry point for API-shaped workloads (the [ALB](services/elb.md) equivalent in front of [Lambda](services/lambda.md)); **three interaction phases** (Request = authorize/validate/transform, Integration, Response = transform/prepare/return); **HTTP / REST / WebSocket** API types with caching and canary **REST-only**; public service so it can front AWS **or** on-premises backends, making it a **migration façade**; **direct AWS service integrations** (DynamoDB, [SNS](services/sns.md), [Step Functions](services/step-functions.md)) with **no backing compute**; **authentication** (open, Cognito user pools with native token validation, **Lambda authorizer** returning an IAM policy + principal — a *different* function from the integration Lambda, IAM credentials-in-headers); **endpoint types** (Edge-optimized = nearest CloudFront PoP, Regional = no CloudFront, Private = interface VPC endpoint + resource policy); **stages** (per-stage settings and endpoint URLs; **deployment** = immutable snapshot with an ID vs **stage** = named pointer; stage names are arbitrary labels; "V1/V2" is a *backend* concept); **canary deployments** (new deploys land on the canary not the base, configurable adjustable traffic split, promote or revert, sticky once enabled); **caching** (per stage, TTL 300 s default / 0–3,600 s, 0.5–237 GB, encryptable, `GET`-only by default, 1 MB max response, ~4 min to provision); **error codes** (400/403/429/502/503/504); **throttling** (10,000 RPS per region, 5,000 burst, usage plans + API keys); - [Kinesis](services/kinesis.md) — Streaming data family; **Data Streams** (the stream as base entity, producers/consumers, **shards** at 1 MB/s or 1,000 records/s in and 2 MB/s or 2,000 records/s out, 1 MB records raisable to 10 MiB since Oct 2025, partition-key hashing and hot shards, the **24-hour-to-365-day rolling persistence window** that makes **replay** possible, **enhanced fan-out** giving each registered consumer its own dedicated 2 MB/s pushed over HTTP/2 via `SubscribeToShard` with 20 consumers per stream or 50 on On-demand Advantage, and the provisioned / On-demand Standard / On-demand Advantage capacity modes), the **Kinesis vs [SQS](services/sqs.md) exam decision** (ingestion + many independent consumers + replay vs decoupling + worker pools + process-once-then-delete); **Firehose** (now *Amazon Data Firehose*; fully managed **delivery**, near real-time on a buffer — 1 MB or 60 s in course terms, 0-second zero buffering and ~5 s delivery in current AWS — optional in-flight [Lambda](services/lambda.md) transform with blueprints and a source-record backup bucket, destinations S3 / Redshift via S3 intermediate plus `COPY` / Elasticsearch-OpenSearch / Splunk / HTTP plus Snowflake and Iceberg today); **Data Analytics** (real-time SQL between an input and an output stream, in-application input/reference/output/error tables, S3 reference-data enrichment, real-time or near real-time depending on the destination — SQL variant **discontinued 27 Jan 2026**, Flink variant renamed **Amazon Managed Service for Apache Flink**); **Video Streams** (live video plus audio/thermal/depth/radar, one stream per camera, Rekognition + Connect integration, raw media unreachable off S3/EBS/EFS)
